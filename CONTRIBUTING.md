# Как помочь курсу

Нашли ошибку, неточность или место, которое трудно понять? Помощь добровольная, и подойдёт любой
из трёх путей: от короткого сообщения до своего pull request (PR). Выбирайте тот, на который есть
время.

| Путь           | Когда подходит                                  | Что нужно                 |
| -------------- | ----------------------------------------------- | ------------------------- |
| Сообщить       | заметили ошибку, но править самим не хочется    | аккаунт GitHub            |
| Быстрая правка | опечатка, формулировка, небольшой фикс примера  | аккаунт GitHub            |
| Большая правка | новый раздел, пример на другом языке, код сайта | аккаунт GitHub, Git, Node |

## Классы правок

Правки различаются не размером, а тем, что решает, права ли она: сам diff, источник, позиция курса
или подача. В шаблонах issue и PR есть раздел «Класс»: отметьте один пункт, и issue или PR получит
метку. Ошиблись с классом — ничего страшного, мейнтейнер переставит.

| Класс                  | Что это                                                            | Путь                   |
| ---------------------- | ------------------------------------------------------------------ | ---------------------- |
| **А. Форма**           | опечатка, пунктуация, разметка, битая ссылка                       | PR сразу               |
| **Б. Ошибка**          | неверный проверяемый факт или неработающий пример кода             | PR сразу, с источником |
| **В. Устарело**        | было верно, но технология или практика изменилась                  | PR сразу, со ссылкой   |
| **Г. Неверная модель** | неверно описано, что это и зачем нужно                             | issue → «принято» → PR |
| **Д. Дискуссионно**    | в отрасли нет единого ответа, а текст подаёт одну позицию как суть | issue → «принято» → PR |
| **Е. Подача**          | верно, но непонятно: порядок, пример, аналогия                     | issue → «принято» → PR |
| **Ж. Согласованность** | противоречие между лекциями или разные термины                     | issue → «принято» → PR |
| **З. Новый материал**  | нужного раздела или темы нет в курсе                               | issue → «принято» → PR |

Г и Д легко спутать. **Г** — у вопроса есть правильный ответ, и его можно подтвердить первичными
источниками: например, Kafka описана как очередь, из которой сообщение исчезает после чтения, хотя
это распределённый лог с повторным чтением. **Д** — правильного ответа нет, есть школы: mock или
fake, монолит или сервисы, нужна ли Kafka там, где хватит RabbitMQ.

**Смысл правится бережно.** Конспект написан по лекциям и одобрен лектором, поэтому:

- неверную модель (Г) обычно уточняют оговоркой рядом, а переписывают только явную ошибку,
  подтверждённую источником;
- спорную позицию (Д) не заменяют: позиция лекции остаётся, рядом появляется блок «Дискуссионно»
  с другим взглядом и его источником;
- подачу (Е) меняют в стиле курса, по его [рубрике](content/service-pages/_internal/editorial-rubric/vitepress.md).

Для Б, В, Г и Д нужен первичный источник: документация, спецификация, книга или статья автора
подхода, вывод компилятора. Для спорного места — источники каждой стороны. Ответ нейросети
источником не считается.

После открытия issue получает метку «нужен разбор». Дальше мейнтейнер ставит одну из меток:
«принято» (можно делать PR), «нужны уточнения», «не будет сделано» (с причиной) или «можно взять»
(принято, и сделать может любой желающий).

## Сообщить об ошибке

Выделите текст на сайте и откройте меню: на компьютере правой кнопкой мыши, на телефоне оно
появится само. Выберите «Сообщить об ошибке». Откроется issue по шаблону «Ошибка в конспекте», где
раздел «Где» уже заполнен: страница, строки исходника и цитата. Остаётся отметить класс и ответить
на три вопроса:

- **Что не так** — наблюдаемое, а не «как-то неудачно». Для примера кода: язык переключателя, что
  ожидали и что получили. Для неверной модели — к какому неверному выводу придёт студент.
- **Как должно быть** — ваш вариант, если он есть.
- **Чем подтверждается** — первичный источник или вывод компилятора. Для опечатки не нужен.

Без сайта можно [выбрать шаблон](https://github.com/Kert0n/KPO/issues/new/choose) самому:

| Шаблон                 | Для чего                                                         |
| ---------------------- | ---------------------------------------------------------------- |
| Ошибка в конспекте     | опечатка, фактическая ошибка, неработающий пример, неясное место |
| Разбор или предложение | новый раздел, переписанное объяснение, пример, диаграмма         |
| Ошибка сайта           | Playground, переключатель языка, диаграммы, поиск, PDF           |

Шаблоны задают порядок мыслей, а не анкету: разделы можно опускать, но каждый оставленный должен
отвечать на свой вопрос. Свободная форма тоже принимается.

## Быстрая правка в браузере

Git ставить не нужно, всё происходит на сайте GitHub.

1. Выделите на странице текст, который хотите исправить, откройте меню и выберите «Исправить
   фрагмент». Выделенный текст скопируется в буфер обмена, а файл страницы откроется в редакторе
   GitHub.
2. При первой правке GitHub предложит **Fork this repository**: это одна кнопка, она создаёт вашу
   копию репозитория.
3. Найдите фрагмент через Ctrl+F (⌘F) и вставьте его из буфера. Исправьте текст.
4. Нажмите **Commit changes…**, коротко опишите правку и выберите **Propose changes**, затем
   **Create pull request**.

Проверки запустятся сами. Если какая-то упадёт, откройте её **Details**: обычно это сломанная
ссылка или разметка. Исправить можно в том же PR, во вкладке **Files changed**.

## Большая правка локально

Для новых разделов, примеров на нескольких языках, диаграмм и правок кода сайта удобнее запустить
сайт у себя. Правки классов Г–З начинаются с issue: дождитесь метки «принято», чтобы не делать
работу зря.

Нужны Git и Node 24 или новее.

```sh
# 1. Сделайте fork репозитория кнопкой Fork на GitHub, затем:
git clone https://github.com/<ваш-логин>/KPO.git
cd KPO
git switch -c fix/lec3-di-example

# 2. Запустите сайт локально и правьте файлы: страница обновляется сама
npm ci
npm run dev

# 3. Перед отправкой проверьте контент и сборку
npm run content:check
npm run build

# 4. Отправьте ветку в свой fork и откройте PR на GitHub
git add content/lectures/Lec3/vitepress.md
git commit -m "Лекция 3: исправлен пример с DI"
git push -u origin fix/lec3-di-example
```

После `git push` GitHub покажет ссылку на создание PR, или откройте свой fork и нажмите
**Compare & pull request**.

Как выглядят примеры на нескольких языках, Playground, диаграммы и другие блоки, видно на странице
[`/intro`](https://kert0n.github.io/KPO/intro). Проще всего скопировать разметку из её исходника
`content/intro/vitepress.md`. Шпаргалка и неочевидные правила собраны в
[`docs/authoring.md`](docs/authoring.md).

### Где лежит текст

| Страница на сайте | Файл в репозитории                   |
| ----------------- | ------------------------------------ |
| `/lectures/03`    | `content/lectures/Lec3/vitepress.md` |
| `/intro`          | `content/intro/vitepress.md`         |
| `/conclusion`     | `content/conclusion/vitepress.md`    |
| `/extras/02`      | `content/extras/02/vitepress.md`     |
| Картинки лекции   | `content/lectures/LecN/assets/`      |

Номер лекции в адресе всегда двузначный: `/lectures/03` собирается из папки `Lec3`.

## Что можно предложить

- фактические ошибки, опечатки, неточные формулировки;
- неработающие или устаревшие примеры кода;
- более понятное объяснение: другую формулировку, пример, диаграмму, таблицу;
- недостающие варианты примеров на других языках из переключателя (Kotlin, C#, Java, Go);
- полезные ссылки в раздел «Дополнительное чтение».

Не стоит присылать перестановку слов без улучшения смысла, массовое переформатирование и правки
кода сайта вместе с правкой лекции: это отдельный PR.

Если используете нейросеть, проверьте результат сами: за содержание PR отвечает его автор.

## Как оформить PR

- Один PR, одна тема: одна ошибка или одно пояснение. Маленькие PR быстрее принимаются.
- Заголовок говорит, что изменилось: «Лекция 3: исправлен пример с DI».
- Описание подставится из шаблона, в том числе в редакторе GitHub:
  - **Класс** — отметьте один пункт; для Г–З сошлитесь на issue с меткой «принято»;
  - **Причина** — что было не так и где: адрес страницы и `Closes #123` для issue;
  - **Что сделано** — было → стало, короткой цитатой до и после: в diff длинные строки текста
    почти не читаются;
  - **Чем подтверждается** — источник, вывод компилятора; как смотрели результат (Preview или
    `npm run dev`); если помогала нейросеть — какая и что вы проверили сами.

  Для опечатки хватит отметки класса и одной строки в «Причине».

## Что будет после открытия PR

1. **Автоматические проверки.** GitHub Actions проверит ссылки, разметку, запускаемые
   Kotlin-примеры и сборку. Если вы впервые вносите вклад в репозиторий, проверки могут ждать, пока
   мейнтейнер их запустит. Если что-то упало, исправьте и отправьте изменения в ту же ветку: PR
   обновится сам, новый открывать не нужно.
2. **Просмотр.** PR посмотрит мейнтейнер. Если он попросит что-то изменить, отвечайте в
   комментариях и отправляйте исправления в ту же ветку.
3. **Merge.** После слияния сайт и PDF курса обновятся автоматически через несколько минут.

## CodeRabbit (по желанию)

[CodeRabbit](https://coderabbit.ai) это AI-ревьюер, который оставляет замечания прямо в PR. Сам он
не запускается. Для смыслового PR (новое объяснение, пример кода, новый раздел, код сайта) его можно
позвать комментарием `@coderabbitai review`. Для опечаток, ссылок и форматирования он не нужен:
квота ревью маленькая и общая на всех.

- Повторный вызов после новых коммитов проверяет только изменения с прошлого ревью.
- За один вызов CodeRabbit проверяет меньше 100 изменённых файлов. Если PR больше, отправляйте его
  порциями и вызывайте ревью после каждой.
- Замечания CodeRabbit — подсказки, а не приказ. Исправьте то, с чем согласны, на остальное ответьте
  в треде. Окончательное решение остаётся за человеком.
