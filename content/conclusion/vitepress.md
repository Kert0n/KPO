# Заключение

Курс сводится к одной практической мысли: конструкция программы должна помогать команде безопасно менять систему. Представьте, что вы выпускаете новую версию приложения магазина. Теперь оно само повторяет запрос на оформление заказа, если покупатель не дождался ответа. Кажется, что вся правка поместится в сетевой клиент. Откуда тогда у покупателя два заказа?

## Один заказ, две попытки

Покупатель нажал «Оформить». Сервер сохранил заказ № 42, но связь оборвалась раньше, чем приложение получило номер. При повторном запросе сервер создал заказ № 43. Оба запроса обработаны без ошибок. С точки зрения покупателя один заказ лишний.

Можно поискать недавний заказ с такой же корзиной. Но через минуту покупатель может сам заказать вторую такую же книгу в подарок. По составу корзины эти две ситуации неразличимы. Приложение знает, повторяет ли оно прежнюю попытку или покупатель снова нажал «Оформить».

Договоримся о правиле. При новом оформлении приложение создаёт уникальный ключ, а при повторе посылает прежний. В нашем магазине сервер помнит ключ сутки. За это время повтор от того же покупателя с тем же ключом и составом корзины должен вернуть номер первого заказа. Если корзина изменилась, сервер сообщает о конфликте. Повтор той же операции в оговорённый срок не создаст второго заказа. Это свойство называют **идемпотентностью**.

Этому обещанию нужна опора в данных. Сервер сохраняет заказ, состав корзины и ключ в одной транзакции. Ограничение уникальности пары «покупатель, ключ» не даст двум одновременным запросам записать по заказу. Если ключ уже занят, обработчик находит сохранённый заказ. При совпадении корзин покупатель получит тот самый № 42.

## Главные идеи курса

| Вопрос при изменении системы | Как рассуждать и что перечитать |
| --- | --- |
| Кто решает, что считать повтором? | Покупатель задаёт намерение, приложение сохраняет ключ, сервис заказов отвечает за результат. Общий язык команды помогает провести эту границу. «Ещё одна попытка» и «ещё один заказ» означают разное. [Ответственность модулей](/lectures/01) · [DDD](/lectures/07) |
| Что придётся переписать при замене хранилища? | Сценарию оформления нужна операция «зарегистрировать заказ или найти прежний». Способ выполнить её атомарно знает реализация хранилища, которую можно передать сценарию извне. [Внедрение зависимостей](/lectures/02) · [Границы архитектуры](/lectures/08) · [Выбор СУБД](/lectures/09) |
| Какой паттерн здесь полезен? | Если библиотека хранения сообщает о повторе своим исключением, [адаптер](/lectures/06#adapter) может перевести его в понятный сценарию результат. При выборе [порождающего](/lectures/04) или [поведенческого паттерна](/lectures/05) назовите конкретную проблему, которую он решает. |
| Как проверить изменение? | Тест через API воспроизводит потерю ответа и сверяет номер и количество заказов. Он останется полезным и после рефакторинга. Одновременную запись стоит отдельно проверить на выбранной СУБД. [Тестирование поведения](/lectures/03) |
| Кто ещё полагается на контракт? | Пока старые приложения работают без ключа, сервер принимает и такие запросы. Если склад получает событие о заказе, обработчик на складе должен распознать повторную доставку и сохранить один резерв товара. История заказов может обновиться позже, если её строят по событиям. [API](/lectures/10) · [Сообщения](/lectures/11) · [Отказоустойчивость](/lectures/12) · [Модели чтения](/lectures/13) |
| Увидим ли мы ошибку после выпуска? | Включайте повторы в приложении, когда все экземпляры сервера понимают ключ. После выпуска повторите оформление с тестового аккаунта. Дождитесь обновления истории покупателя. Два номера для одного оформления выдадут сбой даже при успешных ответах API. [Наблюдаемость и выпуск изменений](/lectures/14) |

## Мини-практика

У покупателя пока нет заказов. Запишите для каждого шага, **что увидит приложение и сколько заказов этого покупателя будет в базе**. Все запросы приходят в течение минуты.

1. Приложение отправило корзину с одной книгой и ключом `A`. Сервер сохранил заказ № 42, ответ потерялся.
2. Приложение повторило тот же запрос.
3. Из-за ошибки приложение отправило две книги с прежним ключом `A`.
4. Покупатель решил оформить ещё один заказ на одну книгу. Приложение отправило ключ `B`.

::: details Сверить результат

1. Приложение не получило номера. В базе один заказ.
2. Приложение получило № 42. В базе по-прежнему один заказ.
3. Приложение получило сообщение о конфликте. У заказа № 42 осталась одна книга, других заказов в базе нет.
4. Приложение получило новый номер. В базе два заказа, в каждом по одной книге.
:::

Проверьте себя ещё на одном сбое. Команда решила сначала записывать заказ, а ключ сохранять отдельным запросом. В какой момент достаточно остановить сервер, чтобы шаг 2 дал другой результат?

::: details Проверить объяснение
Остановите сервер после фиксации заказа и до записи ключа. После перезапуска заказ № 42 существует, но по ключу `A` его найти нельзя. Повтор создаст ещё один заказ. Именно этот промежуток закрывала общая транзакция.
:::

Когда в следующем проекте кто-то предложит временно упростить решение, пройдите с ним один такой сценарий до конца. Что увидит пользователь? Какой тест первым заметит разницу?

И помните:

> Нет ничего более постоянного, чем временное.
